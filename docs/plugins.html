About

Plugins are the true strength of this agent. While the core system provides the brain, plugins give the agent its hands, feet, and specialized tools. Thanks to the simplicity of Tcl language and INI configuration, building a plugin is incredibly straightforward. If you can write a basic script and configure a few lines of text, you can extend the agent's capabilities in minutes.

Directory layout

Plugins are completely modular. To create one, simply drop a single folder containing your .ini and .tcl files into the main plugins directory.

plugins/ └── my_tool/ ├── plugin.ini └── plugin.tcl

How loading works: Discovery is strictly deterministic. The system scans the plugins/ root and registers only the direct child folders. Subfolders inside my_tool/ are ignored during initial discovery, keeping loading fast and predictable.

Manifest

The manifest tells the agent exactly who you are, what your tool does, and when to use it. It defines the contract between your Tcl script and the AI model.

plugin.iniini
[plugin]
name = my_tool
description = Explain clearly when the model should use this tool.
category = filesystem
keywords = inspect,file,workspace
platforms = linux,freebsd,windows
requires = optional-helper
permission = read
entrypoint = plugin.tcl
handler = ::plugins::my_tool::execute
parameters = {"type":"object","properties":{},"required":[],"additionalProperties":false}

Key Configurations Explained:

Smart Tool Selection
The description, category, and comma-separated keywords enable lazy plugin searching, helping the model find your tool instantly when needed.
Strict Argument Validation
The parameters block uses standard JSON Schema. It is shown directly to the model to guide its reasoning and automatically rejects invalid payloads before your script even runs.
Cross-Platform Protection
Specify OS targets with platforms (accepts all, linux, freebsd, or windows). If a user is on an unsupported system, the tool safely registers as unavailable.
Binary Dependencies
Use requires to list external executables that must exist in the user's system PATH.
Tcl Routing
entrypoint defines the script file to source, while handler points to the exact Tcl namespace procedure triggered upon execution.

Note: Plugin name keys must be globally unique. Incompatible or failing plugins will never be exposed to the model.

Tcl handler

The handler is the operational core of your plugin. Written in clean, lightweight Tcl, it receives structured inputs from the model and returns text results back to the system.

plugin.tcltcl
namespace eval ::plugins::my_tool {}

proc ::plugins::my_tool::execute {workspaceRoot arguments settings} {
    return "Tool result"
}

Understanding the Handler Arguments

Your procedure receives three explicit parameters directly from the runtime engine:

workspaceRoot
The absolute path to the configured project root. Use this to safely scope all local file system operations.
arguments
A Tcl dictionary containing the pre-validated arguments sent by the model. These are guaranteed to match your manifest's JSON schema.
settings
A dictionary containing trusted values from the optional [settings] section of your INI file. These values are stripped out before the tool schema is shown to the model.

Best Practices for Execution

  • Keep it concise: Return precise, structured text data. The more noise or unnecessary text you include, the more model context window tokens you consume.
  • Protect secrets: settings data is never logged automatically or seen by the model. Make sure your script logic never accidentally returns raw API keys or passwords back to the execution result stream.

Safety boundary

  • Filesystem paths remain inside the configured workspace.
  • Reference tools such as oodz_read use separate named read-only roots.
  • Write plugins require confirmation for each call.
  • Child interpreters enforce execution deadlines and result limits.
  • Manifest paths and workspace paths reject escapes.
  • Installed Tcl plugins are trusted local code and must be reviewed before installation.

Scoped HTTP tools

The built-in http_get, http_post, http_put, http_patch, and http_delete plugins take only a relative path and optional query dictionary. Their private settings fix the base URL, allowed path prefixes, timeout, maximum response size, and TLS policy. Full URLs, traversal, fragments, embedded query strings, and non-allowlisted paths are rejected.

POST, PUT, and PATCH require a validated JSON-object string; DELETE accepts one optionally. JSON is sent as unchanged UTF-8. All four mutating tools require approval for every request. HTTP status codes and response bodies are returned to the agent.

Add private headers with settings such as header.Authorization = Bearer ... or header.X-API-Key = .... These values are not model-visible. Malformed headers and attempts to override transport-controlled headers are rejected. Protect configuration files that contain credentials.

For private certificates, use tls_verify = true with tls_ca_file pointing to a trusted PEM certificate. A development-only tls_verify = false mode accepts self-signed certificates without authenticating the server; never use it on public or untrusted networks.

GET is treated as read-only and does not require approval. Configure only endpoints where GET does not mutate state.

Fossil tools

Inspect the checkout

fossil_status shows checkout metadata and local changes. fossil_changes gives a concise classified list of managed changes that would enter the next commit. fossil_extras lists unmanaged files using workspace-relative paths and the checkout's ignore policy. fossil_ls lists every managed file with its current status.

fossil_diff shows all uncommitted changes or accepts one confined file. It forces Fossil's internal unified diff engine, preventing checkout configuration from launching an external diff command. fossil_info reports current checkout metadata, and fossil_timeline returns 1–100 recent check-ins. These inspection tools are read-only and do not require approval.

Branches

fossil_branches lists open and closed branches, with Fossil marking the current and private branches. fossil_branch_info accepts one bounded branch name and returns its metadata. Both are read-only.

fossil_branch_new creates a branch from one named basis check-in but does not switch the checkout. fossil_branch_switch switches the entire checkout to one named branch while retaining uncommitted changes. fossil_branch_close marks one branch closed without deleting its history, and fossil_branch_reopen reverses that marker. fossil_merge merges one bounded branch or check-in into the current checkout, keeps undo enabled, and leaves the result uncommitted for review. These operations require approval and disable autosync; merge conflicts may require manual resolution.

Local changes and history

fossil_add schedules one existing confined file for addition. fossil_commit commits all checkout changes using a required bounded message and disables interactive prompts. fossil_update updates the whole checkout to its unique local descendant leaf. These operations require approval and disable autosync.

fossil_revert discards changes in one existing file while preserving Fossil's normal undo snapshot. fossil_undo and fossil_redo restore or reapply one confined path using Fossil's single-level undo state. fossil_remove marks one file removed and deletes it from disk; unlike revert, this explicit hard removal is not recoverable through Fossil's undo stack.

fossil_stash_list lists stash entries and their files without approval. fossil_stash_save saves all current changes with a required bounded comment and reverts the checkout to its baseline. fossil_stash_pop applies and removes the newest stash and may produce conflicts. Save and pop require approval; none of these tools accepts model-selected files or stash IDs.

Execution boundary

Every Fossil plugin uses the configured workspace and controlled process runner, inheriting its timeout, output limit, and execution backend. Local operations perform no implicit network synchronization. fossil_pull and fossil_push are explicit approval-gated network operations that use only the checkout's configured default remote and accept no URL or credentials from the model. Pull changes only the local repository and does not update working files; push sends public sharable changes and excludes private branches.
