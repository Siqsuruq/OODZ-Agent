Two separate roots

The client project remains the writable workspace. OODZ is registered independently as a named, read-only reference root.

RootPurposeAccess
Workspace.rootClient applicationRead and approved writes
OODZ.rootShared framework sourceLookup, search, and read only
conf/conf.iniini
[Workspace]
root = /opt/ns/clients/dev
instructions = AGENT.md

[OODZ]
root = /opt/ns/tcl/oodz

OODZ paths must be relative to the configured reference root. Absolute paths and directory escapes are rejected.

Keep AGENT.md small

AGENT.md contains stable project conventions and is included in every model request. Use it to explain NX inheritance and tell the agent to consult OODZ tools—not to copy full framework documentation.

Workspace/AGENT.mdmarkdown
# Project instructions

This project uses NaviServer, NX, and OODZ.

- Prefer existing OODZ components over replacements.
- Application domain classes normally inherit from `::oodz::baseObj`.
- Use `oodz_lookup`, then `oodz_search` and `oodz_read`, before using an unfamiliar API.

The configured instruction file must be UTF-8, workspace-relative, and no larger than 16 KiB.

Compact capability index

plugins/oodz_lookup/FRAMEWORK_INDEX.json records exact class names, categories, short summaries, keywords, and source paths. It currently describes core objects, SQL builders, database access, date/time, JSON, REST, sessions, storage, UI, HTTP, and security helpers.

Index entryjson
{
  "name": "::oodz::baseObj",
  "category": "database domain objects",
  "summary": "Abstract table-backed domain object...",
  "keywords": ["nx", "domain", "crud", "save2db"],
  "source": "base/baseObj.tcl"
}

Names reflect the real source. Some OODZ classes are namespaced while current SQL builders and ::httpClientClass are global.

Lookup, search, then read

  1. Use oodz_lookup to discover likely components.
  2. Use oodz_search to locate exact methods or properties.
  3. Use oodz_read for only the relevant numbered lines.
  4. Write code in the client workspace using the verified API.
Direct tool examplesoodz
/tool oodz_lookup {"query":"domain object persistence"}
/tool oodz_search {"query":"save2db","path":"base"}
/tool oodz_read {"path":"base/baseObj.tcl","start_line":60,"end_line":130}
Agent tasktext
Create an NX client class using my OODZ framework. It should inherit from the appropriate base class and load client data by identifier. Inspect OODZ before writing code.

Token behavior

The framework directory and full index are not sent automatically. Tool schemas are small and always available; only lookup results, search matches, and source ranges selected during a task enter the conversation.

History matters. Retrieved tool results remain in the active conversation and may be sent again on follow-up requests until history trimming or /new.
  • oodz_lookup returns at most 20 compact entries.
  • oodz_search returns at most 100 short matches and skips .git, tmp, binaries, and files over 1 MiB.
  • oodz_read returns at most 200 numbered lines from a UTF-8 file no larger than 1 MiB.

Maintain the index

When the framework gains a meaningful component, add or update one entry in FRAMEWORK_INDEX.json. Keep summaries short, use terms developers actually ask for as keywords, preserve the exact runtime class name, and point source at a path relative to OODZ.root.

Manual summaries capture intended use better than source scanning. A later generator can refresh structural metadata such as NX classes, superclasses, methods, and properties while preserving these descriptions.
